# Участок медного карьера (команда)

Двойники и симулятор для Концепции из [SUBMISSION.md](../../SUBMISSION.md). Полная схема, список двойников и источники цифр — в [team/docs/design-twins.md](../docs/design-twins.md); здесь только то, что нужно, чтобы запустить и проверить.

```text
Забой-1 (выше Cu) ──[Экскаватор-01]──┐
                                       │ road-face1
                                       ▼
                                Развязка (junction-01) ──road-main-a (основная)──┐
                                       ▲                 ──road-main-b (резерв)──┤──▶ Дробилка CR-01 ──▶ Конвейер ──▶ фабрика (вне модели)
                                       │ road-face2                              │         │
Забой-2 (ниже Cu) ──[Экскаватор-02]──┘                                          ▼         ▼
                                                                            Рудный склад (буфер, если дробилка стоит)

Вскрышной уступ ──[Экскаватор-03]──road-waste──▶ Отвал вскрыши
```

Namespace Ditto: `org.openegiz.pit`. 26 двойников, самосвалы — общий парк, диспетчер переназначает их между тремя экскаваторами через признак `assigned_excavator`.

## Запуск (dev-оверлей этого этапа)

```bash
make team-mine
```

Поднимает платформу (если не запущена) и наш оверлей поверх неё. Двойники — в Grafana → приложение **OpenEgiz** → **Twins**, под namespace `org.openegiz.pit`. `make team-mine-stop` останавливает симулятор, двойники и данные остаются. `make down` / `make up` дальше поднимают и опускают всё вместе, `make clean` забывает оверлей.

Это **не** финальная точка входа для Сборщика — та появится на этапе 23–24.10 (README.md, единая команда). Сейчас это рабочий оверлей для разработки и проверки, по аналогии с `make example-mine`.

## 3D-сцена и панель сценариев

**http://localhost:8091** — Three.js-сцена участка (свой код, не Unity-панель платформы): стилизованный карьер, движущиеся самосвалы, цвет по состоянию. Клик по объекту — карточка двойника справа. Три панели поверх сцены:

- **Сценарии «что если»** (внизу слева) — кнопки на все 4 события из Decision: отказ экскаватора-01/-02, закрытие основной/резервной дороги, остановка дробилки, вывод из строя двух самосвалов (нехватка). У каждого — кнопка отмены. Пока сценарий активен, под кнопкой видно «было → сейчас» по пропускной способности и проценту плана.
- **Диспетчеризация** (внизу, рядом) — выпадающий список у каждого самосвала, переназначает его на другой экскаватор (пишет `assigned_excavator`). Это и есть модуль «диспетчеризация».
- **Контроль качества руды** (внизу справа) — модуль, сравнивающий текущее содержание в подаче (`shift-01.grade_actual`) с минимумом плана и с содержанием по двум забоям, даёт текстовую рекомендацию (на какой забой сместить самосвалы).

### Как это работает технически

Страница — статика (`viewer/public/`), отдаётся своим nginx. Авторизация к Ditto не попадает в браузер: nginx в контейнере вьюера сам добавляет `Authorization: Basic …` (из `DITTO_PASSWORD`, см. `viewer/entrypoint.sh`) ко всем запросам на `/ditto/*`, проксируя на `ditto-nginx`. Это не только безопаснее, но и единственный способ завести Server-Sent Events вообще: у браузерного `EventSource` нет способа самому выставить заголовок `Authorization`, а Ditto как раз и отдаёт live-обновления через SSE на `/api/2/things` (`Accept: text/event-stream`, см. [httpapi-sse](https://eclipse.dev/ditto/httpapi-sse.html)). Запись отдельного признака — обычный `PUT .../features/<feature>/properties/value`.

Three.js (r169) и OrbitControls — не с CDN, а в репозитории (`viewer/public/vendor/`), чтобы сцена открылась и без интернета на машине Сборщика — та же причина, по которой платформа вендорит Grafana-плагины.

Геометрия карьера на сцене — схематичная, подогнанная под граф дорог, а не настоящий рельеф: реальная геометрия Актогая не источник (см. Concept).

## Дашборд Grafana (дополнение к сцене)

Grafana → **Dashboards → Участок карьера → Участок медного карьера (team-025)**. Не замена 3D-сцене — сцена показывает текущий момент, дашборд показывает **историю по смене**, чего на сцене принципиально не видно: тренд подачи на дробилку и содержания (с линией плана), заполнение склада-буфера со временем, топливо по каждому самосвалу, таблицы состояния самосвалов/экскаваторов/дорог.

Код: [generate_dashboard.py](generate_dashboard.py) → `dashboard.json`, по образцу `examples/mine/dashboard.json`. Подключён через собственный provisioning-провайдер Grafana (`deploy/compose/grafana/provisioning/dashboards/openegiz.yaml`, провайдер `team`, папка «Участок карьера» — не смешан с папками платформы или примера) и volume в `compose.yml` (`grafana.volumes`).

**Важный технический нюанс**, из-за которого пришлось переписывать две из трёх таблиц: Flux-функция `pivot()` требует, чтобы столбец `_value`, из которого она строит колонки, был одного типа. Если смешать в одном запросе строковое поле (`state`) и числовые (`trips_total` и т.п.), Ditto/InfluxDB отработают нормально, а вот сам Flux-запрос упадёт с `schema collision detected: column "_value" is both of type string and float` — не ошибка данных, ошибка именно формы запроса. Решение — разделить строковые и числовые признаки на разные `targets` и смержить `joinByField` (ровно так уже сделано у `examples/mine/dashboard.json`, но я не сразу это заметил и один раз наступил на те же грабли). Все 13 панелей проверены напрямую через `influx query` (не только через Grafana) — см. git-историю.

## Как идут данные

```text
simulator.py (SimPy) ──MQTT telemetry/<twin>──▶ Ditto ──MQTT opentwins/#──▶ Telegraf ──▶ InfluxDB ──▶ Grafana
                       ◀──REST GET (опрос, тот же тик, прямо перед публикацией)── Ditto ◀── правки диспетчера (Grafana/Twins)
```

Симулятор публикует полный набор признаков каждого двойника, как и Пример рудника. В отличие от Примера, он ещё и **опрашивает** Ditto: управляемые признаки — `road.state` (open/closed), `excavator.forced_down`, `truck.forced_down`, `truck.assigned_excavator`, `crusher.forced_down` — читаются из Ditto каждые `--interval` секунд, прямо перед публикацией того же тика (один таймер, не два — на живом стенде поймали гонку между независимыми опросом и публикацией, когда публикация успевала затереть правку диспетчера до того, как её подхватит опрос; см. design-twins.md §7), так что правка в Grafana/приложении Twins доходит до симулятора без перезапуска. Почему опрос, а не подписка на поток событий Ditto — см. design-twins.md §5.

`state` у экскаватора/самосвала/дробилки пишет только симулятор (диспетчер не должен его трогать напрямую) — для ручного управления есть отдельный признак `forced_down`. У дорог конкурента-писателя нет, поэтому `state` там задаёт диспетчер прямо.

## Проверка

1. `make team-mine`, подождать, пока три сервиса (`team-mine-setup`, `team-mine-simulator`, `team-mine-viewer`) поднимутся: `make ps`.
2. Twins created: `make logs S=team-mine-setup` — должно быть `26 twins ready`.
3. Телеметрия идёт: `make logs S=team-mine-simulator` — раз в ~15 публикаций строка `sim NNN min | crusher ...`.
4. В Ditto: `curl -u ditto:$DITTO_PASSWORD http://localhost:8080/api/2/things/org.openegiz.pit:crusher-01` — `throughput_tph` должен расти от 0 и выйти на ~2850 т/ч за первый час симулированного времени.
5. В Grafana: Explore → InfluxDB → `mqtt_consumer` с тегом `thingId=org.openegiz.pit:crusher-01` — видны точки с полем `value_throughput_tph_properties_value`.
6. Откройте **http://localhost:8091** — сцена должна загрузиться, самосвалы — двигаться по дорогам, KPI-строка вверху — обновляться. Откройте консоль браузера — не должно быть ошибок `fetch`/`EventSource` (если есть — почти наверняка дело в `/ditto/` проксировании, см. `viewer/nginx.conf.template`).
7. Сценарий «что если», через UI вьюера (кнопка в панели) или напрямую в приложении Twins: `org.openegiz.pit:road-main-a` → `state=closed`. Самосвалы на руде должны пойти через `road-main-b` (на сцене — видно по изменившемуся пути) в течение `--interval` (по умолчанию 2 c); если закрыть и `road-main-b` — встать в `blocked_at_junction`. Обратная команда (или кнопка отмены) — `state=open`.

**Живьём проверено** (`make team-mine` на реальной машине): шаги 1–5 целиком — 26 твинов создаются, симулятор публикует, throughput_tph доходит до ~2850 т/ч и лежит в InfluxDB под правильными именами полей (`value_<feature>_properties_value`) для всех 26 твинов. Вьюер проверен через curl (без браузера, см. ниже) — статика отдаётся, `/ditto/` проксирует REST и SSE без единого запроса пароля от браузера (nginx сам подставляет `Authorization`), формат SSE-событий совпадает с тем, что разбирает `app.js`. Сценарий «что если» — закрытие `road-main-a`, отказ `excavator-01` (`forced_down=true`) — проверены записью через Ditto REST API: экскаватор корректно уходит в `down`, после снятия `forced_down` — восстанавливается.

**Не проверено живьём**: сам рендер WebGL в браузере (shape/цвет/движение самосвалов на экране) — в среде, где это делалось, не было ни браузера, ни расширения claude-in-chrome. Данные, которые вьюер получает, подтверждены точно; то, что Three.js их правильно отрисовывает — нет. Откройте **http://localhost:8091** сами и свяжитесь, если что-то не так (скорее всего в `app.js`, логика позиционирования расписана в design-twins.md §6).

Платформа была остановлена между сессиями (не `make down` намеренно, а просто простой) — после `make team-mine` на чистом старте должно повториться то же самое; если нет, первым делом `make logs S=team-mine-simulator` и `docker compose ... logs telegraf`.

## Что сознательно упрощено

- Опрос Ditto вместо подписки на поток событий (design-twins.md §5) — на несколько секунд медленнее реагирует на ручную правку, зато сильно проще и надёжнее.
- `repair-zone` (ремзона) считает, сколько единиц сейчас в `state=down`, но технику туда физически не возит — экскаватор чинят на месте, самосвал просто выбывает.
- `fuel-station` обслуживает самосвал там, где он есть (мобильный топливозаправщик), а не наоборот — самосвал никуда к ней не едет.
- Расход топлива списывается одним куском в конце плеча, не плавно по ходу движения.
- MTBF/MTTR и надёжность — иллюстративные допущения (небиблиографический источник), не выдаются за точные данные; см. design-twins.md §3.5.

## Переменные окружения симулятора

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MQTT_HOST` / `MQTT_PORT` | `localhost` / `1883` | брокер для публикации телеметрии |
| `DITTO_URL` / `DITTO_USER` / `DITTO_PASSWORD` | `http://localhost:8080` / `ditto` / — | опрос управляемых признаков |
| `SIM_INTERVAL` | `2` | реальных секунд между публикациями (и опросами Ditto — один таймер на оба) |
| `SIM_SPEEDUP` | `10` | симулированных секунд на реальную секунду |
| `SIM_SEED` | `42` | seed генератора случайных чисел |

`python simulator.py --dry-run` печатает сообщения в stdout вместо публикации и не обращается к Ditto — для локальной проверки логики без платформы.
